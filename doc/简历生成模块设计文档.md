## 1. 项目背景与目标

### 1.1 背景

当前系统已经具备以下能力：

- 香港 IT 岗位知识库：JobsDB 等来源的清洗后岗位 JD。
- MongoDB 全文检索与 ChromaDB 向量检索。
- `HybridJobSearch` 混合检索 + rerank。
- 简历 PDF 文本抽取。
- 简历润色 Agent：输入体检、岗位调研、差距分析、润色、评分、面试深挖。

现有简历润色功能的核心假设是：用户已经有一份目标简历，系统围绕目标岗位进行改写和建议。新的需求是：用户上传一份基础简历或个人信息后，系统直接根据应聘岗位和知识库岗位 JD 生成一份完整目标岗位简历。

因此，简历生成功能应作为独立模块建设，而不是简单扩展现有“简历润色”流程。

### 1.2 目标

构建一个知识库驱动的目标岗位简历生成模块，实现：

1. 从用户上传简历 / 粘贴文本中解析个人信息、技能、经历、项目和教育背景。
2. 根据用户输入的目标岗位，从本地知识库召回相似岗位 JD。
3. 聚合目标岗位画像，包括核心能力、高频技能、常见职责、隐性门槛和市场措辞。
4. 从用户真实经历中选择最相关素材，生成面向目标岗位的完整简历。
5. 输出结构化 JSON 与 Markdown 简历，便于前端展示、复制和后续导出。
6. 对生成内容做证据来源标注，避免把知识库 JD 中的要求伪造成用户经历。

### 1.3 非目标

v3.0 MVP 不做以下内容：

- 不做复杂 docx 排版导出。
- 不做长期素材库持久化。
- 不接入 WebSearch。
- 不做多模板简历设计器。
- 不自动保存用户上传简历原文。

## 2. 功能定位与边界

### 2.1 与简历润色的区别

| 维度 | 简历润色 | 简历生成 |
|------|---------|---------|
| 输入 | 已有简历 + 目标 JD / 岗位 | 基础简历 / 个人信息 + 目标岗位 |
| 目标 | 给出改写建议、评分、面试准备 | 直接生成一份完整目标岗位简历 |
| 核心动作 | 优化已有表达 | 选材、组织结构、生成新简历 |
| 输出 | 逐段建议、差距分析、评分 | 完整简历、岗位画像、选材依据、证据审计 |
| 风险 | 过度润色 | 生成内容脱离真实经历 |

### 2.2 输入来源

- PDF 简历：复用现有 `pdf_parser.py` 抽取文本。
- 文本输入：用户直接粘贴个人信息或基础简历。
- 目标岗位：用户输入岗位名称或选择标准角色。
- 目标市场：默认香港 IT 市场。
- 知识库岗位 JD：通过 MongoDB / ChromaDB / HybridSearch 召回。

### 2.3 输出产物

MVP 输出：

- `GeneratedResume`：完整简历结构化结果。
- Markdown 简历文本。
- `TargetJobProfile`：目标岗位画像。
- `CapabilityMatch`：岗位能力与用户真实经历的匹配矩阵。
- `SelectedExperiencePlan`：选材方案，包含选用 / 排除原因。
- `SelectedExperience`：选材依据。
- `ClaimEvidence`：证据来源与风险提示。
- `QualityGateResult`：最小质量闸门结果。
- `similar_jobs`：知识库召回岗位样本。

后续输出：

- docx 简历。
- 多语言版本。
- 公司级定制简历。
- 面试准备包。

### 2.4 核心约束

- 知识库 JD 只能用于理解岗位需求，不得直接写成用户经历。
- 生成的工作经历、项目经历必须可追溯到用户上传材料。
- 对缺乏证据的技能、数字、成果必须标注风险或降级。
- 背调硬信息不得被模型改写，包括学历、公司名、职位、时间。
- 默认不持久化用户上传的简历原文。

### 2.5 参考工作流吸收点

本设计参考现有《简历润色工作流 Agent 设计文档》、`job-hunt-copilot-public.skill` 与 `get-job.skill`，吸收以下原则：

- 从 `job-hunt-copilot` 吸收：长期素材库、基础简历、项目库、按 JD 选择项目、生成前解释选用 / 排除原因。
- 从 `get-job.skill` 吸收：输入体检、岗位调研、能力迁移翻译、证据审计、质量闸门、交付前覆盖矩阵。
- 从现有简历润色工作流吸收：知识库岗位画像、混合检索、市场洞察、SSE 流式输出、面试深挖可衔接能力。

v3.0 MVP 不强制落地长期素材库持久化，但数据模型和工作流应预留 `self_profile`、`resume_base`、`project_library` 三类输入，避免后续重构。

## 4. 工作流设计

### 4.1 主流程

```text
Stage 0 输入体检
→ Stage 1 加载素材：上传简历 + 可选长期素材库
→ Stage 2 个人资料解析 ResumeProfile
→ Stage 3 目标岗位检索 TargetJobProfile
→ Stage 4 能力匹配矩阵 CapabilityMatch
→ Stage 5 选材方案 SelectedExperiencePlan
→ Stage 6 用户确认 / 自动低置信降级
→ Stage 7 简历生成 GeneratedResume
→ Stage 8 证据审计 ClaimEvidence
→ Stage 9 质量闸门 QualityGateResult
→ Stage 10 Markdown 渲染与结果返回
```

### 4.2 Stage 0：输入体检

职责：

- 判断用户是否提供了足够的个人信息。
- 判断目标岗位是否明确。
- 判断是否可以进入知识库模式。

输入：

- `resume_text`
- `target_role`
- `target_role_id`
- `target_market`

输出：

```json
{
  "status": "complete | workable | blocked",
  "resume_status": "provided | partial | missing",
  "target_status": "provided | missing",
  "assumptions": [],
  "gaps": [],
  "blocking_questions": []
}
```

阻塞条件：

- 缺少简历正文或个人信息。
- 缺少目标岗位，且无法从简历推断目标方向。

### 4.3 Stage 1：素材加载

职责：

- 合并本次上传简历与可选长期素材库。
- 为后续选材提供更完整的真实素材。

素材来源：

- `resume_text`：用户本次上传 PDF 或粘贴文本。
- `self_profile`：个人背景、求职偏好、技能标签，后续可持久化。
- `resume_base`：全量基础简历，后续可持久化。
- `project_library`：项目素材库，后续可持久化。

MVP 处理：

- 默认只使用 `resume_text`。
- API 模型预留 `profile_context` / `project_context` 字段，但不自动保存。
- 前端暂不做素材库管理，只展示“后续可补充项目素材”的缺口提示。

### 4.4 Stage 2：个人资料解析

职责：

- 将合并后的素材解析成结构化 `ResumeProfile`。
- 保留原始证据片段，供后续生成和审计使用。

处理内容：

- 联系方式。
- 技能栈。
- 工作经历。
- 项目经历。
- 教育背景。
- 证书 / 奖项。
- 可量化成果。
- 原始片段映射。

### 4.5 Stage 3：目标岗位画像

职责：

- 根据目标岗位构造检索 query。
- 调用 `HybridJobSearch` 召回相似岗位 JD。
- 聚合高频技能、常见职责、隐性门槛和市场表达。

检索优先级：

```text
target_role + target_role_id
→ target_role + resume skills
→ resume current titles + skills
```

知识库边界：

- 有相似岗位：生成 `knowledge_base` 岗位画像。
- 样本少：降低置信度。
- 无相似岗位：要求用户提供目标 JD 或更明确的岗位名称。

### 4.6 Stage 4：能力匹配矩阵

职责：

- 将目标岗位的核心能力与用户真实经历建立映射。
- 判断每个能力是否有真实经历支撑。
- 为后续选材和生成提供“能力 → 证据”底座。

输出：

- `CapabilityMatch` 列表。
- 每个岗位能力的来源依据。
- 对应的工作经历 / 项目 / 技能。
- 证据强度：`strong / medium / weak / missing`。
- 简历表达角度与风险提示。

处理原则：

- 每个核心岗位能力都尝试寻找真实经历锚点。
- 没有锚点的能力不能写入简历，只能进入缺口或补强建议。
- 对跨背景候选人，允许做“能力迁移翻译”，但必须保留真实来源。

能力迁移翻译格式：

```text
真实经历
→ 目标岗位语言
→ 可迁移能力
→ 证据强度
→ 风险提示
```

### 4.7 Stage 5：选材方案

职责：

- 从 `ResumeProfile` 中选择最适合目标岗位的工作经历、项目经历和技能。
- 为每个选中的素材标注目标能力和证据强度。
- 说明哪些素材被排除，以及排除原因。
- 标出需要用户确认的低证据素材。

选材原则：

- 优先真实经历中已有的硬技能和项目成果。
- 优先能映射目标岗位核心能力的经历。
- 不选择无法支撑目标岗位的泛泛经历。
- 不把知识库技能写成用户已经掌握的技能，除非原简历中存在证据。
- 生成最终简历前，应先形成 `SelectedExperiencePlan`；MVP 可自动继续生成，但结果页必须展示选材方案。

### 4.8 Stage 6：用户确认 / 自动低置信降级

职责：

- 让用户理解系统准备选用哪些经历生成简历。
- 对低证据内容自动降级或标记待确认。

MVP 策略：

- 不阻塞主流程，自动继续生成。
- `user_confirmation_required` 中的内容不写成强 claim。
- 生成结果中展示“需确认项”。

后续增强：

- 前端支持用户勾选 / 删除选材项后再生成。
- 支持编辑解析后的 `ResumeProfile`。

### 4.9 Stage 7：简历生成

职责：

- 根据目标岗位画像和选材结果生成完整简历。
- 输出结构化 JSON 和 Markdown。

默认结构：

```text
Name / Contact
Professional Summary
Key Skills
Work Experience
Project Experience
Education
Certifications
```

生成要求：

- 顶部必须包含 `positioning_statement`，即目标导向定位句。
- 每条 bullet 必须带 `bullet_id`、`evidence_id`、`target_capability`。
- 生成结果不得出现 `迁移句:`、`迁移说明:`、`可迁移性:` 等工作痕迹标签。
- 最相关经历优先前置。
- 与目标岗位无关的经历弱化或删除。

语言策略：

- MVP 默认英文。
- 后续支持繁中 / 简中。
- 香港 IT 岗位优先使用英文简历表达。

### 4.10 Stage 8：证据审计

职责：

- 审计生成简历中的 claim。
- 标注每条 claim 的来源、置信度和处理建议。

审计对象：

- 数字。
- 强成果。
- 技能归属。
- 职责升级。
- 公司、职位、学历、时间等背调硬信息。

处理建议：

- `keep`：证据充分，保留。
- `soften`：表达过强，建议弱化。
- `remove`：缺乏证据，应删除。
- `ask_user`：需要用户确认。

### 4.11 Stage 9：质量闸门

职责：

- 在返回最终结果前，执行最小质量检查。
- 防止“看起来很完整，但有造假 / 标签泄漏 / 证据缺口”的简历被当成成品。

P0 红线：

- 编造不存在的公司、学校、职位、项目、时间、数据。
- 改动背调硬信息。
- 把知识库岗位要求写成用户经历。
- 生成内容出现内部标签或模板残留。
- 任一最终 bullet 无法追溯到选材依据。

P1 核心质量：

- 每个岗位核心能力要么有真实经历映射，要么进入缺口说明。
- 每条强动词 / 数字 / 成果 claim 有证据等级。
- 低证据内容有降级、删除或待确认建议。

输出：

- `QualityGateResult.status`: `pass / pass_with_gaps / blocked`
- `p0_violations`
- `p1_gaps`
- `suggested_fixes`

MVP 策略：

- `blocked` 时仍返回中间结果，但不把简历标记为可投递最终版。
- 前端用风险提示展示，而不是静默失败。

## 6. 数据模型设计

### 6.1 请求模型

```python
class ResumeGenerateRequest(BaseModel):
    resume_text: str = Field(..., min_length=50, max_length=50000)
    target_role: str = Field(..., min_length=2, max_length=200)
    target_role_id: str | None = Field(None, max_length=80)
    target_market: str | None = Field("Hong Kong", max_length=100)
    language: Literal["en", "zh-Hant", "zh-Hans"] = "en"
    style: Literal["professional", "technical", "management"] = "professional"
    narrative_angle: Literal["engineering", "ai", "data", "product", "operations", "management"] | None = None
    top_k_jobs: int = Field(8, ge=1, le=20)
    profile_context: dict[str, Any] | None = None
    project_context: list[dict[str, Any]] = Field(default_factory=list)
    auto_continue_without_confirmation: bool = True
```

### 6.2 个人资料模型

```python
class ResumeProfile(BaseModel):
    contact: dict[str, str] = Field(default_factory=dict)
    current_titles: list[str] = Field(default_factory=list)
    target_preferences: list[str] = Field(default_factory=list)
    skills: list[str] = Field(default_factory=list)
    work_experience: list[ExperienceItem] = Field(default_factory=list)
    projects: list[ProjectItem] = Field(default_factory=list)
    education: list[EducationItem] = Field(default_factory=list)
    certifications: list[str] = Field(default_factory=list)
```

## 7. Prompt 设计

### 7.1 个人资料解析 Prompt

目标：

- 从简历原文中提取结构化个人资料。
- 不补写缺失信息。
- 保留原始证据片段。

关键约束：

- 不推断学校、公司、时间。
- 技能必须来自原文或明确上下文。
- 项目经历需保留原始描述，供后续选材。

输出 JSON：

```json
{
  "contact": {},
  "current_titles": [],
  "skills": [],
  "work_experience": [],
  "projects": [],
  "education": [],
  "certifications": [],
  "evidence_snippets": []
}
```

### 7.2 经历选材 Prompt

### 7.2 能力匹配 Prompt

目标：

- 将目标岗位的 3-5 个核心能力映射到用户真实经历。
- 输出 `CapabilityMatch`，标注证据强度和表达角度。

关键约束：

- 能力没有真实素材时，`evidence_strength` 必须是 `missing`。
- `missing` 能力不得进入最终简历正文，只能进入缺口或补强建议。
- 能力迁移必须说明“真实经历是什么”，不能只写岗位关键词。

输出 JSON：

```json
[
  {
    "capability": "Backend API development",
    "job_basis": "Target profile requires FastAPI / REST API experience",
    "matched_sources": ["work_1", "project_2"],
    "evidence_strength": "strong",
    "resume_angle": "Frame internal tooling work as API and workflow automation",
    "risk_note": ""
  }
]
```

### 7.3 经历选材 Prompt

目标：

- 根据 `TargetJobProfile` 从 `ResumeProfile` 中选出最相关素材。
- 标注目标能力、选用原因和证据强度。
- 输出选用和排除原因。
- 标出需要用户确认的内容。

关键约束：

- 不新增用户没有的经历。
- 不因为知识库岗位要求某技能，就假定用户掌握该技能。
- 证据弱的内容应标注 `weak` 或 `risky`。
- 每次生成简历前，必须能说明“选用了哪些项目 / 经历，排除了哪些项目 / 经历，为什么”。

### 7.4 简历生成 Prompt

目标：

- 根据目标岗位画像和选材结果生成完整简历。
- 使用香港 IT 岗位常见英文表达。
- 输出结构化 JSON，不输出解释性文字。
- 生成顶部目标定位句 `positioning_statement`。
- 每条 bullet 输出 `bullet_id`、`evidence_id`、`target_capability`。

关键约束：

- 公司、职位、时间、学历不可改写。
- 不编造数字。
- 允许优化措辞，但不得制造不存在的职责。
- 如果缺少某类内容，可留空，不强行生成。
- 不输出内部工作标签，例如 `迁移句:`、`迁移说明:`、`可迁移性:`。

### 7.5 证据审计 Prompt

目标：

- 审查生成简历中的 claim 是否有来源。
- 对风险内容给出处理建议。

关键约束：

- 对数字和强成果严格审计。
- `knowledge_base` 只能作为岗位需求来源，不能作为用户经历来源。
- `inferred` 内容默认不得直接保留，除非表达足够弱且不涉及硬事实。

### 7.6 质量闸门 Prompt / 规则

质量闸门优先用确定性规则实现，必要时用 LLM 辅助语义检查。

确定性检查：

- 所有 `GeneratedBullet.evidence_id` 必须能在 `SelectedExperiencePlan.selected` 中找到。
- `claim_audit` 中 `risky` 且 `action=keep` 的条目视为 P0 风险。
- 正文不得包含内部标签词：`迁移句`、`迁移说明`、`可迁移性`、`旧版`、`半成品`。
- `knowledge_base` 来源的 claim 不得出现在用户经历描述中。

LLM 辅助检查：

- 检查强动词是否过度包装。
- 检查总结段是否暗示用户拥有未被证据支持的技能。
- 检查生成简历是否像可投递成品，而不是工作记录。

## 10. 真实性与隐私策略

### 10.1 真实性原则

生成简历必须遵守：

- 不编造公司、学校、职位、项目、时间。
- 不编造量化指标。
- 不把知识库 JD 要求写成用户已经完成的事。
- 不把“接触过”写成“主导过”。
- 不把“了解”写成“精通”。

### 10.2 证据来源分级

| 级别 | 含义 | 处理 |
|------|------|------|
| strong | 原简历中有明确证据 | 可保留 |
| medium | 原简历有相关证据，但表达需谨慎 | 可弱化保留 |
| weak | 只有间接线索 | 建议标注或弱化 |
| risky | 缺少证据或可能误导 | 删除或询问用户 |

### 10.3 知识库使用边界

知识库可以提供：

- 岗位要求。
- 关键词。
- 市场常见表达。
- 能力靶心。
- 相似岗位样本。

知识库不能提供：

- 用户实际做过的项目。
- 用户掌握的技能。
- 用户取得的成果。
- 用户工作年限、学历或证书。

### 10.4 隐私策略

- 上传 PDF 仅在请求内存中处理。
- 默认不保存原始简历文本。
- 日志不记录完整简历原文。
- 后续若引入长期素材库，必须增加用户确认流程。

### 10.5 最小质量闸门

生成结果返回前必须执行最小质量闸门：

| 检查项 | 级别 | 失败处理 |
|------|------|---------|
| 编造公司 / 学校 / 职位 / 项目 / 时间 / 数据 | P0 | `blocked` |
| 改动背调硬信息 | P0 | `blocked` |
| 知识库要求被写成用户经历 | P0 | `blocked` |
| 最终 bullet 无 `evidence_id` | P0 | `blocked` |
| 内部标签泄漏 | P0 | 自动修复或 `blocked` |
| 岗位核心能力没有真实经历映射 | P1 | `pass_with_gaps` |
| risky claim 未降级 | P1 | `pass_with_gaps` 或 `blocked` |
| 选材方案未解释排除原因 | P1 | 补齐 |

质量闸门结果不等于“证明用户完全真实”，只表示系统没有主动制造高风险内容，并已标出证据缺口。
