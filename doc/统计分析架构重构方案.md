## 1. 项目背景与目标

### 1.1 背景

当前系统已具备以下能力：

- 角色分类后台线程：逐岗位 LLM 分类（8 并发）+ 行业归类 + 地名归一化，结果写入 `role_cache.json`。
- 技术趋势分析：独立构建 context + LLM 生成 8 段总结，支持磁盘缓存。
- 薪资分析：独立构建 context + LLM 生成 4 段总结，支持磁盘缓存。
- 软技能分析（上一轮新增）：独立分批 LLM 调用提取学历/语言/个人能力。

用户要获得完整的「技术趋势分析」和「薪资分析」，需要在 **3 个页面分别点击**：

| 页面 | 触发动作 | 涉及的 LLM 调用 |
|------|---------|----------------|
| 角色分类 | 点击「分类全部」 | ① 行业归类（50 条批量）② 地名归一化 ③ 逐岗位角色分类（8 并发） |
| 技术趋势 | 点击「重新生成分析」 | ④ 软技能提取（独立批量）⑤ 行业分布（命中磁盘缓存）⑥ 8 段趋势总结 |
| 薪资分析 | 点击「重新生成分析」 | ⑦ 高薪岗位显示名翻译 ⑧ 4 段薪资总结 |

### 1.2 问题

- 用户需点击 3 次，等待 3 轮 LLM 调用。
- 软技能提取是独立批量调用，与角色分类重复阅读 JD，浪费 token 和时间。
- 趋势/薪资页的 context 构建重复读取 `role_cache.json`、重复计算。
- 三个页面的「重新生成分析」按钮职责重叠，用户体验割裂。

### 1.3 目标

- 角色分类页点击一次「分类全部」，全部分析（技术趋势 + 薪资 + 软技能）自动完成。
- 软技能标签随角色分类 LLM 调用同时产出，不再独立批量调用。
- 软技能中文标签持久化到 `role_cache.json`，在岗位浏览页岗位卡片展示。
- 技术趋势页和薪资分析页改为读缓存展示，移除「重新生成分析」主按钮。
- 趋势/薪资分析失败不阻断分类完成，降级为兜底摘要。

## 2. 现状分析

### 2.1 角色分类后台流程

入口：`api/routers/role_stats.py` → `_run_classify_in_background(req)`

```
1. 行业归类（_call_llm_for_industry_batch，50 条批量）
2. 地名归一化（_precompute_location_normalization）
3. 逐岗位分类（ThreadPoolExecutor，8 并发）
   - _do_classify(job, idx)
   - LLM 返回 role_id / role_name / confidence
   - 技能提取（RuleBasedSkillExtractor）
   - 结果写入 _classify_result
4. 缓存写入 role_cache.json（含 _job_id）
5. 进度条到 100%
```

### 2.2 技术趋势分析流程

入口：`api/routers/stats.py` → `tech_trend_analysis(refresh)`

```
1. 构建 context（_build_trend_context）
   - role_demand_ranking（compute_market_insights）
   - role_distribution / role_salary（读 role_cache.json）
   - tech_stack_ranking（读 skills_df）
   - industry_distribution（读磁盘缓存或 LLM 批量）
   - soft_skill_demand（上一轮新增，独立 LLM 批量）
   - responsibility_distribution（规则匹配）
   - knowledge_base_samples
2. LLM 生成 8 段总结（_call_llm_for_trend_analysis）
3. 写入内存缓存 + 磁盘缓存
```

### 2.3 薪资分析流程

入口：`api/routers/stats.py` → `salary_analysis(refresh)`

```
1. 构建 context（_build_salary_context）
   - salary_overview（统计计算）
   - salary_by_location（读 jobs.csv）
   - salary_by_role（读 role_cache.json）
   - top_salary_jobs（读 role_cache.json + LLM 翻译显示名）
2. LLM 生成 4 段总结（_call_llm_sections）
3. 写入内存缓存 + 磁盘缓存
```

### 2.4 软技能分析（上一轮新增，待重构）

入口：`api/routers/stats.py` → `_collect_llm_soft_skill_distribution(df, use_llm)`

```
1. 分批（每批 20 条）让 LLM 阅读全库 JD
2. 提取三类软技能：education / language / soft_skill
3. 归并同义写法为标准中文标签
4. 聚合计数排名
5. 写入磁盘缓存
```

问题：这是独立批量调用，与角色分类流程重复阅读 JD。

### 2.5 行业知识标签识别问题（v1.1 新增）

#### 2.5.1 问题现象

岗位浏览页「行業知識」标签存在系统性误判。以 AS Watson D365 系统集成开发岗（`jobsdb_software_engineer_p3_69`）为例，该岗位被识别出三个错误标签：

| 误判标签 | 触发原因 |
|---------|---------|
| 人工智能/数据服务 | 地名 `Tai Po` 中的子串 `ai `（ai+空格）被规则匹配命中 |
| 保險/財富管理知識 | JD 福利描述 `life insurance coverage` 中的 `insurance` 被命中 |
| 金融/金融科技知識 | JD 电商职责 `payments, promotions` 中的 `payment` 被命中 |

该岗位实际应识别为：零售/电商业务知识、快消（FMCG）行业知识、ERP/D365 系统集成知识——但词库中均无对应词条。

#### 2.5.2 根因分析

**根因 1：LLM 分类覆盖严重不足**

- `role_cache.json` 仅缓存 6 条记录，244 条岗位中 238 条未经过 LLM 分类。
- 岗位浏览页 `_merge_soft_skills_for_row` 查不到 LLM 缓存时，只能 fallback 到规则匹配。
- LLM 分类为手动触发 + 后台异步执行，非自动运行；服务重启后 `_classify_result` 清空。

**根因 2：行业 LLM 批量分类硬编码 `[:50]` 限制**

`_run_classify_in_background` 中调用 `_call_llm_for_industry_batch(industry_records[:50])`，只处理前 50 条岗位。排在第 69 位的 AS Watson 岗位即使触发分类也轮不到 LLM 行业归类，fallback 到规则推断。

**根因 3：规则匹配使用裸子串匹配，无词边界**

`_INDUSTRY_KEYWORD_RULES` 和 `_scan_non_tech_labels_from_text` 均使用 `keyword in text` 做子串匹配，不带词边界（`\b`），导致：

| 关键词 | 误命中文本 | 误判结果 |
|--------|-----------|---------|
| `ai ` | `Tai Po`（t-**ai-空格**） | 人工智能/数据服务 |
| `rag` | `coverage`（c-o-v-e-**r-a-g**-e） | 人工智能/数据服务 |
| `payment` | `payments`（电商支付子串） | 金融/金融科技知識 |

**根因 4：多义词无上下文消歧**

`insurance`、`payment` 等词在不同语境含义不同，但 `_canonical_non_tech_label` 无语境判断：

| 词汇 | 行业语境 | 非行业语境 | 当前归类 |
|------|---------|-----------|---------|
| insurance | 保险行业知识 | 员工保险福利 | 一律归「保險/財富管理知識」 |
| payment | 金融支付 | 电商支付功能 | 一律归「金融/金融科技知識」 |

**根因 5：两套标签体系并存**

行业知识标签有三个来源，标签体系不一致：

| 来源 | 标签体系 | 语言 | 示例 |
|------|---------|------|------|
| ① LLM 角色分类缓存 `role_cache.json` | 繁体 8 类行业知识 | 繁体 | 電商/零售業務知識 |
| ② JD 文本扫描 `_scan_non_tech_labels_from_text` | 繁体 8 类行业知识 | 繁体 | 電商/零售業務知識 |
| ③ 行业规则推断 `_infer_industry_with_rules` | 简体 16 类行业分布 | 简体 | 零售/电商 |

来源③输出的简体行业标签被直接塞入 `domain_knowledge`，与来源①②的繁体行业知识标签并存，导致同一岗位出现语义重复、形态不一的标签。

#### 2.5.3 词库缺口

现有词库缺少以下行业知识分类：

| 缺失分类 | 缺失关键词 |
|---------|-----------|
| 快消/消费品制造 | fmcg、consumer goods、fast-moving |
| 企业应用/ERP 系统集成 | d365、dynamics 365、erp、sap、system integration、middleware |
| 订单/促销/电商运营 | order management、promotion、pricing、catalog |
| 物流履约/TMS | tms、transportation management、fulfillment |

## 3. 目标架构

```
用户在「角色分类」页点击「分类全部」
  │
  ├─ 阶段 1：逐岗位分类（LLM 同时返回角色 + 软技能标签）
  │    ├─ 行业归类（复用现有批量逻辑）
  │    ├─ 地名归一化（复用现有逻辑）
  │    └─ 角色+软技能分类（8 并发，单次 LLM 调用返回 role_id + soft_skills）
  │
  ├─ 阶段 2：构建分析上下文（纯计算，无 LLM）
  │    ├─ 趋势 context：技能/类别/角色分布/行业/软技能聚合/职责/样本
  │    └─ 薪资 context：薪资概览/地区/角色/高薪岗位
  │
  ├─ 阶段 3：LLM 生成智能总结
  │    ├─ 趋势 8 段总结 → 写入磁盘缓存
  │    └─ 薪资 4 段总结 → 写入磁盘缓存
  │
  └─ 完成 → 前端进度条到 100%
       │
       ├─ 技术趋势页：直接读缓存，无「重新生成」主按钮
       └─ 薪资分析页：直接读缓存，无「重新生成」主按钮
```

## 4. 模块详细设计

### 4.1 模块 1：角色分类 Prompt 扩展

**文件**: `src/analyzer/role_prompt.py`

**目标**: 角色分类 LLM 调用同时返回软技能标签，消除独立的软技能批量调用。

**改动**:

修改 `build_role_classify_messages`，返回格式扩展为：

```json
{
  "role_id": "frontend",
  "role_name": "前端開發",
  "confidence": "high",
  "soft_skills": {
    "education": ["學士學位"],
    "language": ["英語", "粵語"],
    "soft_skill": ["溝通能力", "團隊合作"]
  }
}
```

新增软技能提取指引：

1. `education`: 学历要求（例如 学士学位、硕士优先、计算机相关学历、大专或以上 等）
2. `language`: 语言要求（例如 英语、粤语、普通话、中文 等）
3. `soft_skill`: 个人能力（例如 沟通能力、团队合作、组织能力、领导力、问题解决、抗压能力、跨团队协作 等）

归并规则：

- 学历统一用中文表达，归并同义写法（如 Bachelor's degree / 学士学位 都写成「學士學位」）。
- 语言统一用中文，归并同义写法（如 English / 英语 都写成「英語」，Cantonese 写成「粵語」，Mandarin 写成「普通話」，Chinese 写成「中文」）。
- 个人能力统一用中文，归并同义写法（如 communication → 沟通能力，teamwork → 团队合作，organizational skills → 组织能力，problem-solving → 问题解决）。

更新 few-shot 示例，覆盖软技能返回。

### 4.2 模块 2：角色分类器解析软技能

**文件**: `src/analyzer/role_classifier.py`

**目标**: 角色分类器解析并持久化软技能标签。

**改动**:

- `RoleResult` dataclass 增加 `soft_skills: dict[str, list[str]]` 字段，默认 `{"education": [], "language": [], "soft_skill": []}`。
- `_classify_with_llm` 解析返回 JSON 中的 `soft_skills` 字段，缺失时回退为空字典。
- `classify()` / `classify_batch()` 把 `soft_skills` 写入 `role_cache.json`。
- `role_cache.json` value 结构扩展：

```json
{
  "role_id": "frontend",
  "role_name": "前端開發",
  "confidence": "high",
  "soft_skills": {
    "education": ["學士學位"],
    "language": ["英語", "粵語"],
    "soft_skill": ["溝通能力", "團隊合作"]
  },
  "_job_id": "jobsdb_xxx"
}
```

- `_classify_with_rules` 返回空 `soft_skills`。
- 缓存命中时读出 `soft_skills`。

### 4.3 模块 3：后台分类线程集成全部分析

**文件**: `api/routers/role_stats.py`

**目标**: 后台分类线程在分类完成后，继续执行趋势分析和薪资分析。

这是改动的核心。`_run_classify_in_background` 在现有分类完成后，继续执行阶段 2 和 3：

```python
# 现有：分类完成，_classify_result 填充完毕
# ↓ 新增 ↓

# 阶段 2-3：生成趋势分析和薪资分析
_classify_progress = {
    "running": True, "progress": 95, ...,
    "message": "正在生成技術趨勢分析..."
}
try:
    from api.routers.stats import (
        _generate_trend_analysis,
        _generate_salary_analysis,
    )
    # 趋势分析
    _generate_trend_analysis(df)
    # 薪资分析
    _classify_progress["message"] = "正在生成薪資分析..."
    _generate_salary_analysis(df)
except Exception as e:
    logger.warning("Post-classification analysis failed: %s", e)
    # 不阻断分类完成，趋势/薪资页回退到兜底摘要
```

**`_do_classify` 函数改动**:

- 缓存命中时从 `role_cache.json` 读出 `soft_skills`，写入 `_classify_result` 每条岗位。
- LLM 分类时解析 `soft_skills` 并存入缓存。

**`ClassifiedJob` 结构扩展**（`api/schemas/role_stats.py` 和前端 `classification.ts`）:

新增 `soft_skills` 字段：

```typescript
soft_skills?: {
  education: string[]
  language: string[]
  soft_skill: string[]
}
```

### 4.4 模块 4：统计接口适配

**文件**: `api/routers/stats.py`

#### 4.4a 删除独立软技能批量调用

- 删除 `_collect_llm_soft_skill_distribution`（上一轮新增的独立批量函数）。
- 删除 `_call_llm_for_soft_skill_batch`、`_job_soft_skill_record`、`_soft_skill_cache_signature`。

#### 4.4b 新增软技能聚合函数

新增 `_aggregate_soft_skills_from_cache()`:

- 从 `role_cache.json` 读取全部已分类岗位的 `soft_skills`。
- 按三类（`soft_skill` / `education` / `language`）聚合计数排名。
- 个人能力 top 10 / 学历 top 6 / 语言 top 6。
- 带磁盘缓存，签名基于 `role_cache.json` 的 mtime + 岗位数。

### 4.6 模块 6：全量 LLM 分类覆盖与旧缓存保留（v1.1 新增）

**目标**：角色分类按钮点击时执行全量分析（覆盖全部岗位），分类完成前用户看到的是上一次的缓存数据。

#### 4.6a 行业 LLM 分类去掉 `[:50]` 限制

**文件**: `api/routers/role_stats.py` → `_run_classify_in_background`

**现状**：

```python
llm_industry = _call_llm_for_industry_batch(industry_records[:50])
```

只处理前 50 条，其余 fallback 到规则推断。

**改动**：

改为分批处理全部岗位，每批 50 条：

```python
industry_by_idx: dict[int, str] = {}
batch_size = 50
for start in range(0, len(industry_records), batch_size):
    batch = industry_records[start:start + batch_size]
    try:
        assigned = _call_llm_for_industry_batch(batch)
        industry_by_idx.update(assigned)
        # 更新进度
        _classify_progress = {
            ..., "message": f"正在歸類行業... {start + len(batch)}/{len(industry_records)}",
        }
    except Exception as e:
        logger.warning("Industry LLM batch %d-%d failed: %s", start, start + len(batch), e)
        for record in batch:
            industry_by_idx[int(record["idx"])] = _infer_industry_with_rules(record)
```

同理，`_collect_llm_industry_distribution`（`api/routers/stats.py`）中的 `llm_records = records[:50]` 也改为全量分批。

#### 4.6b 分类期间不清空 `_classify_result`

**文件**: `api/routers/role_stats.py` → `_run_classify_in_background` / `classify_jobs`

**现状**：

```python
# _run_classify_in_background 开头
_classify_result = []  # 立即清空，用户看到空列表

# classify_jobs 接口
_classify_result = []  # 立即清空
```

**改动**：

- 不在分类启动时清空 `_classify_result`，保留上一次的完整结果。
- 分类期间 `/api/stats/classify-progress` 返回 `running=True` 且不返回 `results`（因为新结果尚未就绪）。
- 前端 `resumeOnMount` / 轮询逻辑中，`running=True` 时不清空 `results.value`，保留旧数据展示。
- 分类完成后，`_classify_result` 被整体替换为新结果，前端轮询检测到 `running=False` 时加载新结果。

```python
# classify_jobs 接口
# 删除: _classify_result = []
# 保留旧数据，仅重置进度状态
_classify_progress = {"running": True, "progress": 0, ...}

# _run_classify_in_background
# 删除开头的 _classify_result = []
# 仅在分类全部完成后替换: _classify_result = results
```

#### 4.6c `full` 模式不删除磁盘缓存文件

**文件**: `src/analyzer/role_classifier.py` → `clear_cache` / `api/routers/role_stats.py`

**现状**：

```python
# _run_classify_in_background
if req.mode == "full":
    classifier.clear_cache()  # 删除 role_cache.json，清空内存缓存
```

`clear_cache` 会 `os.remove(CACHE_PATH)`，导致分类期间磁盘缓存丢失，其他页面（如岗位浏览）读到空缓存。

**改动**：

`full` 模式改为「跳过缓存命中、强制重新分类」，但不删除磁盘文件：

```python
# _run_classify_in_background
if req.mode == "full":
    # 不删除磁盘缓存，仅标记强制重新分类
    classifier._force_reclassify = True
else:
    classifier._force_reclassify = False
```

`_do_classify` 中缓存命中判断增加 `_force_reclassify` 检查：

```python
if not getattr(classifier, '_force_reclassify', False) and cache_key in classifier._cache:
    # 使用缓存
else:
    # 重新分类
```

分类完成后，新结果逐条覆盖写入 `role_cache.json`，磁盘文件始终保持有效数据。

#### 4.6d 前端 `startClassify` 保留旧结果

**文件**: `web/src/stores/classification.ts` → `startClassify`

**现状**：

```typescript
async function startClassify(batchSize = 5) {
  results.value = []  // 立即清空
  // ...
}
```

**改动**：

```typescript
async function startClassify(batchSize = 5) {
  running.value = true
  progress.value = 0
  // 删除: results.value = []
  // 保留旧结果，分类期间用户仍可查看上一次数据
  message.value = '正在啟動分類任務...'
  // ...
}
```

`_startPolling` 轮询中，`running=True` 时不更新 `results.value`；仅在 `running=False` 且 `data.results` 有值时替换为新结果。

## 5. 数据流与缓存策略

### 5.1 数据流

```
role_cache.json（核心数据源）
  ├─ role_id / role_name / confidence / soft_skills / _job_id
  │
  ├─→ /api/jobs 关联 → JobCard 展示软技能标签
  │
  ├─→ _aggregate_soft_skills_from_cache() → 软技能排名
  │      └─→ tech_trend context.soft_skill_demand
  │
  ├─→ role_distribution() / role_salary() → 角色分布/薪资
  │      └─→ tech_trend / salary context
  │
  └─→ industry_distribution（磁盘缓存）→ 行业分布
         └─→ tech_trend context
```

### 5.2 缓存失效策略

- `role_cache.json` 更新（重新分类）→ 所有派生缓存失效。
- 缓存签名基于 `role_cache.json` mtime + `jobs.csv` mtime + 岗位数。
- `_TREND_ANALYSIS_CONTEXT_VERSION` / `_SALARY_ANALYSIS_CONTEXT_VERSION` 升版使旧缓存失效。
- 后台分类线程主动写入新缓存，签名与接口读取一致。
- **v1.1 补充**：`full` 模式不再删除 `role_cache.json` 磁盘文件，改为 `_force_reclassify` 标记跳过缓存命中。分类期间磁盘文件始终保持上一次的有效数据，岗位浏览等其他页面不受影响。新结果逐条覆盖写入，分类完成后文件原子性更新。

### 5.3 缓存层级

| 层级 | 位置 | 内容 | 失效条件 |
|------|------|------|---------|
| L1 | `role_cache.json` | 每岗位角色 + 软技能标签 | 重新分类覆盖写入（v1.1：不再删除文件） |
| L2 | 内存缓存（`_trend_analysis_cache` / `_salary_analysis_cache`） | 趋势/薪资完整结果 | 签名不匹配 |
| L3 | 磁盘缓存（`ai_analysis_cache.json`） | 趋势/薪资完整结果 | 签名不匹配 |
| L4 | 磁盘缓存（`soft_skill_distribution`） | 软技能聚合排名 | `role_cache.json` mtime 变化 |
| L5 | 内存（`_classify_result`） | 分类完整结果列表 | 分类完成后整体替换（v1.1：分类期间不清空） |

## 7. 容错策略

### 7.1 分析失败不阻断分类

阶段 2-3 用 `try/except` 包裹，失败时记录日志，分类仍标记完成。趋势/薪资页回退到兜底摘要。

### 7.2 LLM 不可用

- 分类走规则引擎，`soft_skills` 为空。
- 趋势/薪资走本地兜底摘要（现有逻辑不变）。

### 7.3 缓存部分命中

趋势分析成功但薪资失败时，趋势页正常显示，薪资页显示兜底摘要。用户仍可在薪资页手动点击「刷新」重试。

### 7.4 后台线程异常退出

分类后台线程意外终止时，`_classify_progress["running"]` 置为 `False`，前端轮询检测到非运行状态后恢复 UI。

### 7.5 分类期间旧数据可见（v1.1 新增）

- 分类启动时不清空 `_classify_result` 和 `results.value`，用户在分类期间仍可查看上一次的分类结果。
- `role_cache.json` 磁盘文件在分类期间不被删除，岗位浏览页、技术趋势页、薪资分析页等依赖该缓存的页面不受影响。
- `full` 模式通过 `_force_reclassify` 标记强制重新分类，新结果逐条覆盖写入磁盘，保证文件始终有效。
- 分类完成后 `_classify_result` 整体替换为新结果，前端轮询检测到 `running=False` 时加载新数据。

## 11. 标签质量治理技术方案

### 11.1 背景问题

以 `System Analyst (AI Team)` JD 为例，现有标签提炼存在以下质量问题：

| 问题类型 | 现象 | 风险 |
|---------|------|------|
| 关键场景缺失 | 未突出流程自动化、办公自动化、内部工具开发、旧系统集成、中间件、降本增效 | 岗位画像偏向普通 AI/云开发，无法表达真实业务需求 |
| 示例技能被当成强要求 | JD 写明 Python essential，但 JavaScript/TypeScript/Go/Java 只是 “at least one other major language” 示例，现有标签全部平铺为技术栈 | 技能统计会夸大可选语言需求 |
| 推断标签未分层 | `rag` 合理相关但 JD 未显式出现；`英語` 只来自英文 JD，而非明确语言要求 | 用户难以区分明确要求、合理推断和弱证据标签 |
| 标签归类不准 | `llama` 与 `llamaindex` 混淆；OpenAI 被放入框架与库；AI 概念与厂商/API 未拆开 | 趋势分析与筛选维度失真 |
| 误判标签未抑制 | `風險合規知識` 没有 JD 证据；`insurance/payment` 等词可能来自福利或电商语境 | 岗位浏览页出现错误行业知识 |
| 业务能力覆盖不足 | Product engineer mentality、cost/labor reduction、non-technical stakeholder communication 没有结构化沉淀 | 简历匹配和趋势摘要丢失高价值软性要求 |
| 售前方案型 JD 语义丢失 | 政府客户、水处理设施、传感器品牌指定、IT 基础设施、ISO 27001、投标、POC 被压缩成泛化的 AI / Digital Twin / IT 标签 | 无法识别售前解决方案工程师、政府/公用事业行业经验和合规方案能力 |
| 跨行业复合背景被压扁 | 香港岗位常见“技术 + 行业客户 + 业务流程 + 合规/系统对象”的复合要求，例如金融支付、电商履约、物流 TMS、医疗系统、地产物业、教育平台、政府项目 | 只统计技术词会丢失行业迁移价值，简历匹配无法区分“会 Python”和“会在特定行业场景落地 Python” |

### 11.2 目标

- 标签输出从“字符串列表”升级为“证据驱动的结构化标签”，每个标签保留来源、证据、置信度和要求层级。
- 明确区分 `required`、`preferred`、`example`、`inferred` 四类标签，避免把示例和推断当成硬性要求。
- 扩展标签体系，覆盖 AI 自动化岗位常见的业务场景：流程自动化、旧系统集成、RPA、Cron、Web Scraping、成本优化、内部工具开发。
- 扩展售前解决方案岗位标签，覆盖政府/公共部门客户、传感器选型、水处理设施、IT 基础设施、网络安全、ISO 27001、投标、技术提案、演示和 POC。
- 建立跨行业复合标签模型，把行业客户、业务场景、技术方案、交付动作、合规标准、系统/设备对象分开抽取，再组合成岗位画像。
- 建立规则后处理层，对 LLM 和规则提取结果做统一归一、消歧、黑名单抑制和低置信过滤。
- 前端展示默认突出高置信、明确要求标签，详情页允许查看可选/推断标签和触发证据。

### 11.5 Prompt 改造

**文件**：`src/analyzer/role_prompt.py`

角色分类 Prompt 在返回 `soft_skills` 的同时，增加 `tag_profile`。核心约束：

1. 必须引用 JD 原文短证据；没有证据的标签不得输出为 `required`。
2. 对 `e.g.`、`such as`、`like`、`one of` 后面的技能标为 `example`，除非句子同时出现 `must`、`essential`、`required`。
3. `preferred qualifications`、`nice to have`、`familiarity with` 标为 `preferred`。
4. `essential`、`required`、`proficiency in`、`experience with` 标为 `required`。
5. 合理但未明说的标签只能标为 `inferred`，置信度不得高于 0.7。
6. 不要从福利、地点、公司介绍中提取行业知识；优先从 responsibilities、requirements、qualifications 中提取。
7. 售前、投标、方案演示、技术提案、POC 等动作应归入 `presales_delivery` 或 `business_skill`，不要只归为“沟通能力”。
8. 政府标准、ISO 27001、network security 等应归入 `security_compliance`，但只有 JD 明确出现 security / compliance / ISO / government standards 时才输出。
9. 传感器、设备状态监测、水处理设施应保留行业场景组合，不要只输出单个 `Sensors`。

### 11.6 后处理与误判抑制

新增 `src/analyzer/skill_postprocessor.py`，统一处理 LLM 和规则输出。

处理步骤：

1. **标准化**：大小写归一、同义词归并、繁简展示名统一。
2. **分类纠偏**：按 `skill_taxonomy.py` 的标签定义重分配分类，例如 OpenAI → `ai_api`，LlamaIndex → `ai_framework`。
3. **要求层级修正**：根据 evidence 中的 `essential|required|preferred|e.g.|such as|familiarity` 修正 `requirement_level`。
4. **负例抑制**：命中福利、地点、公司介绍、免责声明上下文时降低置信度或删除。
5. **多义词消歧**：`payment` 在 ecommerce/order/promotion/catalog 上下文中归为电商业务，不归金融；`insurance` 在 benefits/coverage 上下文中不归保险行业知识。
6. **置信度门槛**：岗位卡片默认展示 `confidence >= 0.75` 且 `requirement_level in {"required", "preferred"}` 的标签；统计分析默认只统计 `required/preferred`。

负例规则示例：

| 词 | 抑制语境 | 处理 |
|----|---------|------|
| `ai` | `Tai Po`、`chair`、`available` 等词内子串 | 不触发 AI 标签 |
| `rag` | `coverage`、`average` 等词内子串 | 不触发 RAG |
| `insurance` | `life insurance coverage`、`medical insurance` | 不触发保险行业知识 |
| `payment` | `payments, promotions, order management` | 归入电商/零售业务知识，不归金融 |

### 11.7 统计与展示策略

**统计分析**：

- `tech_stack_ranking` 默认只统计 `required` 与 `preferred`，不统计 `example`。

- `inferred` 单独计入“相关技术方向”，不与明确要求混排。

**技术趋势页**：

- AI 相关图表拆分为：AI API、AI 框架、AI 概念，避免 OpenAI、LangChain、LLM 混在同一层级。

### 11.10 跨行业复合标签治理模型

政府/水处理/传感器售前 JD 只是一个典型例子。香港 IT 岗位中，大量职位并不是纯技术岗位，而是“技术能力 + 行业客户 + 业务流程 + 系统对象 + 合规约束 + 交付动作”的复合型岗位。标签系统需要先拆维度，再组合画像。

#### 11.10.1 六维抽取模型

每条 JD 除了技术栈外，应额外抽取以下六个维度：

| 维度 | 说明 | 示例 |
|------|------|------|
| `industry_context` | 服务的行业、客户类型或业务领域 | 金融/银行、保险、零售/电商、物流、医疗、教育、地产/物业、政府/公共部门、环保/公用事业 |
| `business_scenario` | 具体业务流程、业务对象或落地场景 | 支付、订单、促销、履约、库存、客户服务、投标、审批、风控、设备监测、水处理 |
| `solution_domain` | 技术方案类型或系统方案方向 | AI 方案、Digital Twin、ERP、CRM、D365、TMS、IT 基础设施、数据平台、内部自动化 |
| `delivery_motion` | 岗位交付动作 | 需求分析、方案设计、售前演示、技术提案、POC、投标、系统集成、实施交付、运维支持 |
| `compliance_standard` | 合规、标准、安全、审计要求 | ISO 27001、PDPO、AML/KYC、SFC/HKMA 相关合规、政府标准、信息安全合规 |
| `system_or_asset` | 被建设、集成、监控或维护的系统/设备对象 | 传感器、机械设备、POS、支付网关、仓储系统、楼宇系统、医疗系统、ERP、网络设备 |

#### 11.10.2 从词匹配升级为“上下文窗口 + 角色动作”匹配

跨行业标签不能只靠关键词。例如 `payment` 可能是金融支付，也可能是电商订单支付；`insurance` 可能是保险行业，也可能是员工福利；`sensor` 可能是 IoT，也可能是水处理设施设备监测。后处理需要使用上下文窗口判断“这个词在做什么”。

建议规则：

| 触发模式 | 标签判断 |
|---------|----------|
| `payment` + `banking/fintech/KYC/AML/card/wallet` | 金融/金融科技业务知识 |
| `payment` + `order/promotion/catalog/ecommerce/retail/POS` | 电商/零售业务知识 |

| `ISO/PDPO/AML/KYC/SFC/HKMA/government standards` | 合规标准标签，保留具体标准名 |

#### 11.10.5 统计分析适配

技术趋势页应拆分两类统计：

| 统计类型 | 用途 |
|---------|------|
| 技术频次统计 | Python、AWS、Docker、SQL、React 等纯技术趋势 |
| 场景化能力统计 | 金融支付系统、零售 ERP 集成、政府投标/POC、物流 TMS、设备状态监测等跨行业能力趋势 |

趋势摘要生成时，应避免只说“AI 和云平台需求高”，而要表达：

- 哪些行业场景正在吸收 AI / 数据 / 自动化能力。
- 哪些技术需要配合行业系统或合规标准落地。
- 哪些岗位更偏售前方案、系统集成、内部自动化、平台开发或交付实施。

#### 11.10.6 通用验收标准

新增标签系统应满足：

- 同一个 JD 可以同时拥有多个行业/业务场景，但每个标签必须有证据。
- 行业标签和技术标签分层展示，不互相覆盖。
- 统计榜单中不把 `PowerPoint`、`Excel`、`MS Office` 与工程技术栈混排。
- `preferred`、`example`、`inferred` 不进入硬性要求统计。
- 跨行业组合画像必须由至少两个证据维度支持。
- 福利、地点、公司介绍、隐私声明不参与行业知识提取。

### 11.11 Taxonomy Discovery Agent 设计

固定匹配词库无法覆盖香港跨行业岗位的所有业务场景。系统需要在角色分类链路中增加一个“词库发现 Agent”，让 LLM 在阅读 JD 时发现新标签、新别名、新行业场景和新组合画像，但只写入候选区，不直接修改正式词库。

#### 11.11.1 插入位置

当前角色分类主链路：

```
/api/stats/classify-jobs
  └─ api/routers/role_stats.py::_run_classify_in_background
      ├─ 行业归类
      ├─ 地名归一化
      ├─ 并发逐岗位 _do_classify(job, idx)
      │   ├─ RoleClassifier._classify_with_llm(classify_text)
      │   ├─ RuleBasedSkillExtractor.extract(...)
      │   └─ 写入 classifier._cache[cache_key]
      ├─ classifier._save_cache()
      ├─ _generate_trend_analysis(df)
      └─ _generate_salary_analysis(df)
```

Agent 的最佳插入点：

1. **单条发现节点**：`_do_classify` 中，`_classify_with_llm` 返回之后、`classifier._cache[cache_key]` 写入之前。
2. **批量汇总节点**：`_run_classify_in_background` 中，全部 `future` 完成之后、`_generate_trend_analysis(df)` 之前。

不建议插入的位置：

| 位置 | 原因 |
|------|------|
| `api/routers/stats.py::_scan_non_tech_labels_from_text` | 已经进入统计 fallback 阶段，太晚，且会导致每个页面重复扫描 |
| `src/analyzer/rule_engine.py::RuleBasedSkillExtractor` | 该模块适合稳定词库匹配，不适合发现新概念 |
| 前端岗位卡片/详情页 | 前端只能展示结果，不应承担 JD 理解和词库演化 |

#### 11.11.4 词库文件设计

新增目录：

```text

```

文件职责：

| 文件 | 职责 |
|------|------|
| `skill_taxonomy.json` | 正式词库，只由人工确认或自动晋升规则写入 |
| `taxonomy_candidates.json` | 候选标签池，来自 LLM 发现结果 |
| `taxonomy_aliases.json` | 术语别名映射，如 `Proof-Of-Concept` → `POC 測試` |
| `taxonomy_rejections.json` | 被拒绝的误判词和负例语境，如福利里的 insurance |

#### 11.11.5 并发与写入策略

`_run_classify_in_background` 当前使用 `ThreadPoolExecutor(max_workers=8)` 并发分类。为避免多个线程同时写候选词库文件：

- 单条 `_do_classify` 只把 `taxonomy_candidates` 写入该岗位的缓存 entry，或追加到线程安全内存队列。
- 不在 `_do_classify` 内直接写 `data/taxonomy/*.json`。
- 等所有 `future` 完成后，主线程调用：

```python
taxonomy_agent.consolidate_candidates(
    job_results=results,
    role_cache=classifier._cache,
)
```

批量汇总节点负责：

1. 合并同名标签与别名。
2. 去掉低置信、无证据、福利/地点/隐私声明来源的候选。
3. 与正式词库、别名库、拒绝列表比对。
4. 更新 `taxonomy_candidates.json` 和 `taxonomy_discovery_log.jsonl`。
5. 给趋势分析提供最新的候选场景统计，但不让候选自动进入核心技术榜单。

#### 11.11.6 候选晋升机制

LLM 只能提出候选，不能直接污染正式词库。候选进入正式词库必须满足以下条件之一：

| 晋升方式 | 条件 |
|---------|------|
| 人工确认 | 管理界面或脚本确认候选标签 |
| 高频自动晋升 | `support_count >= 3`，且来自至少 2 个不同公司，平均置信度 `>= 0.85` |
| 别名自动合并 | 候选被判定为正式标签别名，且证据语境一致 |
| 永久拒绝 | 命中 `taxonomy_rejections.json` 或人工拒绝，后续同语境不再推荐 |

候选不得自动晋升的情况：

- `requirement_level = inferred`。
- 没有 JD 原文证据。
- 证据来自福利、地点、隐私声明、公司介绍。
- 只是过长短语或一次性项目描述，无法作为可复用标签。
- 与正式词库已有标签语义重复但未建立 alias。

#### 11.11.7 Agent 工具与职责边界

`TaxonomyDiscoveryAgent` 不负责最终角色分类，也不替代规则词库。它只做三件事：

1. **发现**：找出现有词库没有覆盖、但 JD 证据明确的新标签。
2. **归并**：判断新词是否是已有标签别名或相邻概念。
3. **暂存**：把高质量候选写入候选池，等待汇总、审核或晋升。

建议类接口：

```python
class TaxonomyDiscoveryAgent:
    def process_job(self, job: dict, role_result: RoleResult, taxonomy_snapshot: dict) -> dict:
        ...

    def validate_candidate(self, candidate: dict, jd_text: str) -> dict | None:
        ...

    def consolidate_candidates(self, job_results: list[dict], role_cache: dict) -> dict:
        ...
```

`process_job` 可复用角色分类 LLM 的返回，优先在 `role_prompt.py` 中要求同一次 LLM 输出 `candidate_taxonomy_updates`。如果 token 或质量不稳定，再拆为第二次轻量 LLM 调用。

#### 11.11.8 角色分类 Prompt 扩展

`build_role_classify_messages` 需要新增输出字段：

```json
{
  "role_id": "...",
  "role_name": "...",
  "confidence": "high",
  "soft_skills": {},
  "tag_profile": {},
  "cross_industry_profile": {},
  "job_context_profile": {},
  "candidate_taxonomy_updates": [],
  "candidate_alias_updates": []
}
```

Prompt 约束：

- 只提议可复用标签，不提议完整句子。
- 每个候选必须有 `evidence`。
- 已存在于词库的标签不进入 `candidate_taxonomy_updates`。
- 不确定但有业务价值的概念标为 `candidate`，不标为正式标签。
- `inferred` 标签可以进入岗位画像，但不能自动进入候选晋升池。

#### 11.11.9 与统计分析的关系

趋势分析应分三层使用标签：

| 数据来源 | 使用方式 |
|---------|----------|
| 正式词库命中的 `tag_profile` | 进入正式趋势统计 |
| 候选词库中的高置信场景标签 | 进入“新兴场景/待确认标签”模块 |
| 单条 JD 的 `taxonomy_candidates` | 只用于岗位详情和发现日志，不进入主榜单 |

这样既能让系统发现新行业词，又不会让一次误判污染市场趋势。

#### 11.11.10 落地优先级

第一期只做“候选发现 + 缓存沉淀”：

- 扩展 Prompt。
- 扩展 `RoleResult`。
- 写入 `role_cache.json`。
- 生成 `taxonomy_candidates.json`。
- 不改前端审核界面。

第二期做“统计消费 + 管理审核”：

- 趋势页增加“新兴场景标签”。
- 管理页增加候选词库审核。
- 支持确认、合并别名、拒绝候选。

第三期做“自动晋升”：

- 按 `support_count`、公司数、置信度、拒绝列表自动晋升低风险候选。
- 晋升后更新正式词库并触发派生缓存失效。

### 11.12 政府/公用事业售前解决方案 JD 验收样例

针对包含以下职责的 JD：

- 为政府客户的水处理设施推荐和指定合适传感器品牌，用于监测和跟踪机械物理状况。
- 设计覆盖网络、硬件、软件和网络安全的 IT 基础设施解决方案，确保可靠运行并符合政府标准。

- 与业务发展经理合作，通过演示、方案设计、技术提案、方案演示和 POC 测试开发业务机会。
