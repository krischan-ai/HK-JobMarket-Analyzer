#### 2. 数据清洗与重建脚本

脚本流程：
1. 读取 JobsDB 原始 JSON。

8. 覆盖写入清洗后的 CSV。
9. 导入 MongoDB。
10. 使用 Qwen embedding 重建 ChromaDB 向量索引。

安全控制：
- 脚本要求显式传入 `--confirm-clear`，避免误清库。

#### 6. 混合检索

新增文件：
- `src/knowledge_base/hybrid_search.py`

1. MongoDB 全文检索。

5. 调用 rerank 模型重排序。
6. rerank 不可用时回退到融合排序。

### v2.7 — 简历润色 Agent MVP 落地与 PDF 简历增强规划（2026-06-24）

**状态**: 已提交  
**提交**: `739b63c`（`v2.7 feat(resume): add resume polish agent and frontend page`）  
**目标**：在原《简历润色工作流 Agent 设计文档》基础上，先交付可运行的简历润色 MVP，再扩展 PDF 简历读取、知识库岗位上下文增强和前端上传体验。

---

#### 1. 初始规划回顾

设计文档目标：
- 构建简历润色工作流 Agent，作为 HK-JobMarket-Analyzer 内置功能模块运行。
- 工作流节点：简历解析 → JD 分析 → 岗位匹配 → 差距分析 → 润色生成 → 评分验证。
- 复用现有基础设施：
  - `LLMConfigManager`：读取 LLM API Key / Base URL / Model。
  - `RoleClassifier`：目标 JD 角色分类。
  - `VectorStore`：从 ChromaDB 召回相似岗位。
  - 知识库岗位数据：作为香港 IT 市场表达与技能关键词参考。
- 模型配置原则：
  - 简历润色 Agent 不提供独立模型配置。
  - 统一使用系统设置页中的 LLM 配置，即 `LLMConfigManager` 管理的 API Key / Base URL / Model / Timeout。
  - 前端简历润色页面不暴露模型选择项；如需换模型，应到系统设置页修改全局 LLM 配置。
- 输出产物：
  - 逐段润色建议。
  - 技能差距分析。
  - JD 关键词覆盖建议。
  - 相似岗位参考。
  - 多维评分报告。

### 1. JobResearch：知识库驱动的岗位调研

目标：先用本地 MongoDB / ChromaDB / HybridSearch 构建“香港市场岗位画像”，后续再可选接入 WebSearch 补充具体公司官网、最新 JD、面经和新闻。

推荐分层：
```text
JobResearch
├─ KB Research：基于本地岗位知识库分析香港 IT 市场共性需求
└─ Web Research：后续可选，补公司级、部门级、最新面经与动态
```

知识库可支撑的调研内容：
- 目标岗位画像：同类岗位常见 title、职责、年限、学历、语言要求。
- 核心能力关键词：从 `skills`、`jd_text`、`kb_document_text` 聚合高频技能。
- 技术栈趋势：Python、AWS、Azure、LangChain、RAG、MLOps 等出现频次。
- 角色方向判断：AI 应用开发、后端、DevOps、数据、Technical PM 等。
- 香港市场措辞：常见英文 JD 表达、responsibilities / requirements 句式。
- 相似岗位样本：召回 5-10 条代表性岗位作为依据。
- 简历改写靶心：收敛成 3-5 个核心能力关键词。
- 置信度与缺口：如果样本少，标注低置信，不把市场画像伪装成具体公司结论。

边界：
- 知识库能回答“香港市场类似岗位通常要什么”。
- 单靠知识库不能回答“某公司这个具体岗位最新要求是什么”。
- 用户提供 JD 时，JD 是最高优先级；未提供 JD 时，知识库生成“市场岗位画像”。

### 2. 当前简历工作流与 `get-job.skill` 的主要差距

#### 2.1 缺 Stage 0 输入体检

`get-job.skill` 在进入调研或改写前会先判断输入状态：
- 目标公司 / 岗位是否明确。
- 目标市场 / 语言是否明确。
- JD 是否完整。
- 简历是否完整。
- 是否已经投递。
- 是否已有面试轮次。

建议新增 `InputHealth` 层：
```text
InputHealth
- target_company
- target_role
- target_market
- jd_status
- resume_status
- application_status
- interview_stage
- assumptions
- blocking_questions
```

状态分级：
- `Complete`：目标岗位、市场/JD、简历、投递状态足够明确，直接进入对应阶段。
- `Workable`：有缺口但不阻塞，自动推断、知识库补齐、低置信标注后继续产出。
- `Blocked`：缺少目标岗位或简历正文等硬输入，继续会误导，只问最少必要问题。

#### 2.2 缺岗位调研作为润色前置阶段

当前 v2.8 的 `market_context` / `market_insights` 多作为润色过程中的内部上下文。下一步应独立成 `JobResearch` 阶段，作为简历改写和面试准备的共同输入。

阶段产出建议：
- `岗位调研.md` 或前端 `岗位调研` Tab。
- 目标市场与来源覆盖说明。
- 3-5 个核心能力关键词。
- 同类岗位高频技能与职责。
- 隐性门槛与风险点。
- 简历改写靶心。
- 低置信 / 待确认缺口。

#### 2.3 缺“简历 bullet → 面试准备”的下游闭环

`get-job.skill` 要求最终简历每一条 bullet 都进入面试准备，并具备：
- 30 秒讲法。
- 60-90 秒展开版。
- 2-4 个追问。
- 证据口径。
- 二三层追问兜底。
- 不能说什么。
- 风险等级。

建议新增 `ResumeBulletInventory`：
```text
ResumeBulletInventory
- bullet_id
- final_text
- target_capability
- evidence_source
- evidence_confidence
- talk_track_30s
- follow_up_questions
- risk_notes
- fallback_answer
```

前端可新增结果 Tab：`面试深挖`。

#### 2.4 缺证据化审计与风险地图

当前 prompt 已强调“不编造经历”，但尚未结构化追踪 claim 证据。

建议新增 `ClaimEvidence`：
```text
ClaimEvidence
- claim
- claim_type: number / role / skill / achievement
- source: resume / project_library / user_confirmed / inferred
- confidence: strong / medium / weak / risky
- action: keep / soften / remove / ask_user
- interview_strategy
```

处理原则：
- 每个数字、强动词、成果 claim 都要有来源或降级策略。
- 讲不清来源的数字模糊化或删除。
- 学历、在职时间、职位名称、公司名等背调硬信息不改。
- 市场 JD 中出现的技能不能直接写成用户经历，除非用户简历或项目素材中已有证据。

#### 2.5 缺质量闸门和回归评测

`get-job.skill` 把质量拆成 P0 / P1 / P2，并提供 `quality_check.py` 与固定回归场景。当前项目已有功能测试，但缺求职语义层面的 eval。

建议质量闸门：
- P0 红线：造假、背调硬信息改动、低质量来源冒充事实、过度包装、标签泄漏。
- P1 核心质量：JD 核心能力必须映射到真实经历；每条最终 bullet 必须有面试讲法和证据状态；低置信内容必须标注。
- P2 体验质量：文件名、结构、扫读体验、语言自然度。

建议回归场景：
- 完整 JD + 完整简历。
- 无 JD，仅目标岗位。
- 简历已投，不允许改写，只准备面试。
- 用户承认某个数字记不清。
- PDF 简历 + 知识库模式。
- 香港岗位 + 英文 JD。
- 轮次未知，不能硬生成 HR 面 / 二面 / 三面。

## v3.0 规划：知识库驱动的目标岗位简历生成功能

**状态**：规划中  
**规划日期**：2026-06-25  
**核心诉求**：根据用户上传简历中的个人信息、经历与技能素材，结合应聘岗位和本地知识库岗位 JD，直接生成一份面向目标岗位的完整简历。该功能不是“简历润色”和“修改建议”，而是新的“简历生成”链路。

---

### 1. 功能边界

与现有简历润色 Agent 的区别：
- 简历润色：用户已有一份简历，系统围绕目标 JD 给出逐段改写、差距分析、评分和面试深挖。
- 简历生成：用户上传简历或个人信息作为素材库，系统根据目标岗位画像和知识库 JD，直接生成一份新的目标岗位简历。

输入来源：
- 用户上传 PDF 简历或粘贴个人信息。
- 用户填写 / 选择目标岗位，例如 `AI Engineer`、`Backend Developer`、`MLOps Engineer`。
- 可选目标市场，默认香港 IT 市场。
- 本地 MongoDB / ChromaDB / HybridSearch 召回的知识库岗位 JD。

输出产物：
- 一份完整目标岗位简历，优先输出结构化 JSON 与 Markdown。
- 目标岗位画像：相似岗位样本、高频技能、常见职责、核心能力靶心。
- 选材依据：哪些个人经历 / 项目被用于支撑目标岗位。
- 证据提醒：哪些内容来自原简历，哪些是推断，哪些需要用户确认。

核心原则：
- 知识库 JD 只能提供岗位需求、市场表达和关键词，不得直接变成用户经历。
- 生成简历必须基于用户上传材料中的真实经历、技能、教育和项目。
- 低证据内容必须降级、标注或要求用户确认。
- 默认不持久化保存用户上传简历原文。

---

### 2. 推荐目标工作流

```text
上传 PDF 简历 / 粘贴个人信息
→ ResumeProfile 解析个人背景、技能、经历、项目、教育
→ 用户选择或填写目标岗位
→ HybridJobSearch 从知识库召回相似岗位 JD
→ TargetJobProfile 聚合目标岗位画像
→ ExperienceSelector 从个人素材中选择最相关经历
→ ResumeGenerator 生成完整目标岗位简历
→ ClaimEvidenceAudit 审计生成内容证据来源
→ 前端展示 / 复制 / 导出 Markdown
```

建议与现有润色流程共用底层能力，但保持独立入口：
- 复用 `pdf_parser.py` 做 PDF 文本抽取。
- 复用 `HybridJobSearch` / `market_context` / `market_insights` 做知识库岗位画像。
- 复用 LLM 配置 `LLMConfigManager`。
- 复用后续 `ClaimEvidence` / 质量闸门思想，但生成链路独立于 `/api/resume/polish`。

### 3. 后端模块规划

建议新增或扩展 `src/resume_agent/` 下的生成链路模块：


```python

    target_capability: str
    evidence_text: str
    selection_reason: str
    evidence_confidence: Literal["strong", "medium", "weak", "risky"]

class GeneratedResume(BaseModel):
    language: Literal["en", "zh-Hant", "zh-Hans"]
    headline: str
    summary: str
    skills: list[str]
    work_experience: list[GeneratedExperience]
    projects: list[GeneratedProject]
    education: list[GeneratedEducation]

class ResumeGenerationResult(BaseModel):

    claim_audit: list[ClaimEvidence]
    similar_jobs: list[dict]
```

#### 10. v3.3 补充修复：AI 分析卡死与薪资总结消失

**问题一：点击栏目卡在“AI 分析中”，切换其它栏目也被拖住**

原因：
- 普通统计接口（地名归一化、行业归类、薪资岗位显示名）会同步触发 LLM，导致任意栏目都可能被模型请求阻塞。
- 薪资分析命中缓存时直接 `return`，未把 `salaryAnalysisLoading` 复位，页面永远停在“AI 分析中”。

修复：
- 普通统计接口只读已有缓存和本地规则，不再临时调用 LLM；趋势/薪资 AI 分析改为“有缓存直接返回 → 无缓存先返回本地兜底摘要 → 仅点击‘重新生成分析’才真正调用 LLM”。
- `web/src/stores/stats.ts` 为趋势/薪资请求加 `AbortController`，切换页面时取消旧请求；命中缓存的快速返回路径强制复位 `loading=false`。
- 趋势/薪资页首屏数据与 AI 分析分开加载，离开页面（`onBeforeUnmount`）自动取消对应 AI 请求。

**问题二：薪资分析里所有 AI 总结整块消失（本次根因）**

原因：
- 缓存中 LLM 返回的 `evidence` 字段类型不一致——`salary_overview`/`salary_by_location`/`salary_by_role` 为**字符串**，仅 `top_salary_jobs` 为数组。
- 上一轮重构的 `salaryEvidenceLabels()` 执行 `(section.evidence || []).slice(0,8).map(...)`：`.slice()` 作用在字符串上仍返回字符串，字符串没有 `.map()` → 渲染期抛 `TypeError`，导致 `el-row` 的 `v-for` 整块渲染失败，所有卡片消失。
- 旧代码是 `v-for` 直接遍历 `.slice()`（字符串按字符遍历），只是显示难看但不崩溃；重构成 `.map()` 后由“难看”变成“整页崩溃”。

修复（三层防御）：
- 前端 `web/src/views/SalaryAnalysisPage.vue` 的 `salaryEvidenceLabels()` 先把 `evidence` 统一成数组（数组原样、字符串按 `、；;`/换行拆分、其它类型置空），`.map()` 不再作用于字符串。
- 后端 `api/routers/stats.py` 新增 `_normalize_evidence()` / `_normalize_sections()`：
  - `_call_llm_sections()` 返回前规整，**写入**缓存的即为干净数组；
  - `_get_disk_cached_analysis()` 读取时规整，**旧缓存**无需重新生成也会被清洗成数组。
- `TechTrendsPage.vue` 存在同类 `.evidence.slice().map()` 写法，但趋势 evidence 始终为后端构造的列表，不会触发该崩溃，本次保持不动。

### 1. 根因 3/4/5 与词库缺口修复

修改文件：
- `api/routers/stats.py`

#### 1.1 根因 3：裸子串匹配无词边界

问题：`_infer_industry_with_rules` 与 `_scan_non_tech_labels_from_text` 使用 `keyword in text` 裸子串匹配，导致：
- `ai ` 命中 `Tai Po`（地名）→ 误判「人工智能/数据服务」
- `rag` 命中 `coverage`（insurance coverage）→ 误判「人工智能/数据服务」
- `payment` 命中 `payments`（电商支付）→ 误判「金融/金融科技」
- `health` 命中 `health checks`（系统健康检查）→ 误判「医疗健康」（文档未提及的新误判）

修复：
- 新增 `_has_cjk(text)` 判断字符串是否含中文字符。
- 新增 `_word_boundary_match(keyword, text)`：英文关键词用 `\b` 正则匹配，中文关键词保留 `in` 子串匹配。
- 改造 `_infer_industry_with_rules`：3 处 `keyword in text` → `_industry_keyword_hit`。
- 改造 `_scan_non_tech_labels_from_text`：domain_knowledge 类用 `_industry_keyword_hit`，其余类别用 `_word_boundary_match`。
- 改造 `_canonical_non_tech_label` domain_knowledge 分支：英文关键词词边界匹配。
- 将 `_INDUSTRY_KEYWORD_RULES` 中 `"ai "` / `" ai/"` 修正为 `"ai"`，配合词边界正则避免误命中。

#### 1.2 根因 4：多义词无上下文消歧

问题：`insurance`、`payment`、`medical`、`health`、`wealth` 在不同语境含义不同，但无语境判断：
- `insurance` 在「life insurance coverage」（员工福利）与保险行业知识间一律归「保險/財富管理知識」
- `payment` 在电商支付功能与金融支付间一律归「金融/金融科技知識」

修复：
- 新增 `_BENEFIT_CONTEXT_WORDS` 元组：coverage、benefit、pension、life insurance、medical insurance、health check、post-release、system health 等福利/技术语境词。
- 新增 `_is_non_industry_context(text, keyword)`：检查关键词命中点前后 40 字符窗口内是否出现福利/技术语境词。
- 新增 `_POLYSEMY_INDUSTRY_KEYWORDS` 集合：`{insurance, medical, health, payment, wealth}`。
- 新增 `_industry_keyword_hit(keyword, text)`：词边界匹配 + 多义词消歧组合判定，多义词命中福利/技术语境时跳过。

#### 1.3 根因 5：两套标签体系并存

问题：
- 来源③ `_INDUSTRY_KEYWORD_RULES` 输出简体 16 类（如「零售/电商」「互联网/软件服务」）。
- 来源①② `_canonical_non_tech_label` 输出繁体 8 类（如「電商/零售業務知識」）。

## 2026-06-27 补充记录（二）：跨行业复合标签 LLM 全量回填

### v3.5-p2 - 让每个 JD 都经 LLM 提炼标签画像（依要求层级）与跨行业六维画像

**背景**：验收方案（`doc/JD标签分类验收方案.md`）要求每个岗位 JD 都输出
`tag_profile`（依 required/preferred/example/inferred 层级）、`cross_industry_profile`
（六维）、`job_context_profile.summary_tags`（跨行业组合画像）与 `taxonomy_candidates`
（候选词库）。实测发现系统的组合画像长期只有「政府公用事業 AI/Digital Twin 售前解決方案」
一种，疑似未覆盖全部岗位。

#### 1. 根因诊断

核对 `data/role_cache.json`（248 条）实际内容：

- 仅 3 条有 `tag_profile`、2 条有 `cross_industry_profile`、1 条有 `summary_tags`，
  所有标签 `source` 均为 `rules`。
- 即整库由**规则降级引擎**生成，LLM 从未真正参与；而规则引擎只对售前解决方案样本
  （`_classify_cross_industry_solution_rules`，需 ≥3 个 presales 信号）产出六维画像，
  故唯一的 summary_tag 即来自 `COMBINATION_RULES` 首条规则名。
- LLM 提示词（`role_prompt.py`）本身已完整要求上述四类结构化输出，只是从未被执行。

#### 2. 三处缺陷修复

**2.1 `full` 模式无法真正重跑 LLM（致命）**

`api/routers/role_stats.py::_do_classify` 在调用 LLM 前**无条件**读缓存，未检查
`_force_reclassify`，导致 `mode=full` 下旧的规则缓存被直接复用、LLM 永不触发。

- 修复：缓存命中判断改为 `if not classifier._force_reclassify and cache_key in ...`。
- 保留"不删缓存、原地覆盖"语义：每条算完即覆盖写回，其他页面读到的始终是旧值或新值，
  不出现空缓存/加载中状态（满足"重跑时用户看到缓存界面"的体验要求）。

**2.2 LLM 在并发下大面积超时静默降级**

实测 8 并发 + 30s 超时下，DeepSeek 几乎每个请求 Read timeout（31-52s），
`_classify_with_llm` 捕获后回退规则引擎（返回空标签），"成功"结果其实都是降级产物。

- `_get_classifier()`：classifier 超时 30s → 90s。
- `_run_classify_in_background`：LLM 模式并发 `min(8,total)` → `min(4,total)`，
  规则模式保持高并发。
- 修复后回填实测 237/244 走 LLM，仅 7 条降级（2.9%）。

**2.3 长 JD 响应被 `max_tokens` 截断**

售前/架构/管理类长 JD 的结构化输出可达 6000-9700 字符，撞 `max_tokens=8192`
导致 JSON 截断、解析失败后降级规则。

- `src/analyzer/role_classifier.py::_call_api`：`max_tokens` 8192 → 16384。
- 7 条降级均属此类；本次按"不重跑 LLM"要求保留其规则结果，修复仅对后续分类生效。
